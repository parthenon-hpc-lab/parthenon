# Callback DAGs: Dependency-Ordered Package Callbacks

## Goal

Let packages declare the order in which their callbacks run relative to other
packages. Before this change, every per-package callback (`FillDerived*`,
`EstimateTimestep*`, `PostInitialization*`, ...) ran in the iteration order of
`Packages_t`, which is not under the user's control. A package whose `FillDerived`
needs a quantity computed by another package's `FillDerived` had no way to say so;
the usual workaround was to merge the two into one callback or to move the
computation into an unrelated hook.

The feature should:

- let a package say "run my callback after X" and "run my callback before Y" when it
  registers the callback, without editing X or Y;
- order each callback independently, since packages relate differently in different
  callbacks;
- keep existing registrations (`pkg->FillDerivedMesh = MyFill;`) compiling and
  behaving as before;
- be a general utility, so downstream codes can order callbacks of their own types
  the same way.

## Design

### `CallbackRegistration<Func>` (`utils/callbacks.hpp`)

A callback plus its dependencies:

```cpp
template <typename Func>
struct CallbackRegistration {
  Func callback = nullptr;
  std::vector<std::string> depends_on;   // run after these
  std::vector<std::string> required_by;  // run before these
  CallbackRegistration &Register(Func fn, const std::vector<std::string> &after = {},
                                 const std::vector<std::string> &before = {});
  CallbackRegistration &operator=(Func fn);  // no dependencies
  template <typename... Args> auto operator()(Args &&...args) const;
  explicit operator bool() const;
  friend bool operator==(const CallbackRegistration &, std::nullptr_t);
};
```

- Dependencies are package names, so a package can depend on another without
  including its headers or sharing types.
- Both directions are supported. "Before" lets a package put itself ahead of a
  package it doesn't own, which "after" alone can't express.
- `operator=`, `operator()`, `operator bool` and comparison with `nullptr` make a
  registration a drop-in replacement for the `std::function` it wraps, so existing
  assignments, null checks and calls keep compiling. Assigning a plain function
  clears any dependencies, so reassigning never keeps stale ordering.

### `CallbackDAG` (`utils/callbacks.{hpp,cpp}`)

A small directed graph of names with a DFS topological sort. Before sorting it
checks for cycles and throws with the cycle's path, e.g.
`Cyclic dependency detected: hydro -> eos -> hydro`, so a bad registration fails loudly at
the first call rather than silently picking an order. It can also write itself in
GraphViz DOT format for debugging. It knows nothing about callbacks or packages.

### `CallbackOrder<T>` (`utils/callbacks.hpp`)

Orders the callbacks of a set of named `T`s. It is built from any map of names to
(smart) pointers to `T`, so it works directly on `Packages_t`'s dictionary or a
downstream `std::map<std::string, std::shared_ptr<Unit>>`.

```cpp
template <auto Member> requires CallbackMemberOf<Member, T>
OrderedCallbacks<Member> Callbacks() const;

template <auto Member> requires CallbackMemberOf<Member, T>
void WriteCallbackGraph(std::ostream &stream, const std::string &callback_name) const;
```

`Callbacks<Member>()` returns a range over the registrations of one callback member,
in execution order. Iterating it yields the registrations themselves, so the loop
body calls them directly.

Rules applied when building the order:

- only items that register the callback are ordered;
- dependencies on items that don't register that callback, or don't exist, are
  ignored, so packages can name optional packages;
- cycles throw, naming `T` (e.g. "Error building execution order for
  StateDescriptor callbacks: Cyclic dependency ...");
- items with no dependency between them run in an unspecified order.

### `StateDescriptor` and `Packages_t`

- Every per-package callback on `StateDescriptor` is a
  `CallbackRegistration<std::function<...>>`.
- `Packages_t` forwards `Callbacks<Member>()` and `WriteCallbackGraph<Member>()` to a
  `CallbackOrder<StateDescriptor>`, also available from `CallbackOrders()`.
- `CallbackOrder<StateDescriptor>` is explicitly instantiated in
  `state_descriptor.cpp` and declared `extern template` in `state_descriptor.hpp`.
  The graph building and sorting are not templated on the member, so they are
  compiled once rather than in every file that loops over callbacks.
- `MeshOrBlock<T>(mesh_member, block_member)` picks the Mesh or Block member for a
  data type `T`, for code templated on `MeshData`/`MeshBlockData`.
- Every place Parthenon calls a package callback loops over `Callbacks<Member>()`:
  derived-field fills and timestep estimates (`update.hpp`), refinement checks,
  newly allocated sparse variables, post-problem-generator and post-initialization
  (`mesh.cpp`), user work before the loop and before outputs, and step diagnostics.

## Design decisions

### Member pointers as the selector

Callbacks are selected with a pointer to member as a template argument
(`Callbacks<&StateDescriptor::FillDerivedMesh>()`) rather than a string name or a
getter lambda:

- the `CallbackMemberOf` concept rejects non-callback members at compile time;
- the result is typed, so the loop calls the registration with its real signature,
  with no casts or lookups;
- downstream types work without registering their members anywhere.

Overloaded wrapper methods on `StateDescriptor` (`FillDerived(MeshData *)`,
`FillDerived(MeshBlockData *)`, ...) used to choose the variant by overload
resolution. They can't produce a member pointer, so they were replaced by
`MeshOrBlock`, and the wrappers were removed rather than left as an unordered way to
call callbacks.

### Rebuild the order on every call

The order is rebuilt from the current registrations each time `Callbacks` is called.
Caching was considered and rejected: packages can be added and registrations
reassigned at any point, and detecting that needs hashing or invalidation hooks on
every registration. That is a lot of code and room for stale-order bugs, compared
with a sort over a handful of packages. Rebuilding means registrations can be
changed at any time and the next call sees them.

### Order each callback separately

Each callback member has its own graph. Ordering several members together (e.g. the
Mesh and Block variants of `PostInitialization` as one graph, so dependencies cross
between them) was considered and dropped: it needed variadic member lists throughout
the API, and merged dependencies are harder to reason about. Instead the Mesh and
Block variants are separate loops, with all Mesh callbacks running before any Block
callback. A package should still register only one variant, and Parthenon still
throws if both are set.

### General utility, compiled once for Parthenon

The ordering code is in `utils/` and templated on `T` so downstream codes can reuse
it for their own unit types. The explicit instantiation keeps Parthenon's own
compile cost the same as a non-template implementation.

## Usage

### Registering with dependencies

```cpp
// Runs after "eos" and before "hydro", if those packages register FillDerivedMesh
pkg->FillDerivedMesh.Register(MyFill, /*after=*/{"eos"}, /*before=*/{"hydro"});

// No dependencies, same as before
pkg->EstimateTimestepMesh = MyTimestep;
```

The advection example uses this: the app's `FillDerivedBlock` computes a field that
the advection package's `FillDerived` reads, so it registers with
`/*before=*/{"advection_package"}`.

### Calling callbacks in order

```cpp
for (const auto &fill_derived_mesh :
     packages.Callbacks<&StateDescriptor::FillDerivedMesh>()) {
  fill_derived_mesh(md);
}
```

In code templated on the data type:

```cpp
for (const auto &fill_derived :
     packages.Callbacks<MeshOrBlock<T>(&StateDescriptor::FillDerivedMesh,
                                       &StateDescriptor::FillDerivedBlock)>()) {
  fill_derived(rc);
}
```

Name the loop variable after the callback, e.g. `check_refinement_mesh`, dropping
the suffix when `MeshOrBlock` selects it.

### Debugging the order

```cpp
packages.WriteCallbackGraph<&StateDescriptor::FillDerivedMesh>(std::cout,
                                                               "FillDerivedMesh");
```

### Downstream types

```cpp
struct Unit {
  CallbackRegistration<std::function<void()>> Setup;
};
std::map<std::string, std::shared_ptr<Unit>> units = ...;
CallbackOrder<Unit> order(units, "Unit");  // "Unit" names T in errors
for (const auto &setup : order.Callbacks<&Unit::Setup>()) {
  setup();
}
```

## Migration

- Assignments, null checks and direct calls on callback members are unchanged.
- Calls to the removed wrappers (`pkg->FillDerived(rc)`, `pkg->EstimateTimestep(rc)`,
  ...) become loops over `Callbacks<Member>()`. Those loops skip unregistered
  packages, so no null check is needed.
- Code that copies a callback member into a `std::function` uses `.callback`.
- Packages that set both the Mesh and Block variant of `PostProblemGenerator` or
  `PostInitialization` already threw. Packages that set one each now see all Mesh
  variants run before all Block variants, rather than alternating package by package.
